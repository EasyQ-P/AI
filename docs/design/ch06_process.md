## 6.1 시스템 아키텍처

### 6.1.1 구성

[그림: 시스템 아키텍처 — 브라우저, EC2(frontend · auth · backend · worker), RDS, S3, 외부 AI API, Gmail SMTP, EC2 호스트 SSH 터널, 학과 서버(학습서버 · 판정 추론) — 다시 그림]

EasyQ는 서비스 서버, 서비스 DB, AI학습서버의 세 부분으로 구성한다.

- **서비스 서버(AWS EC2 1대, Ubuntu 22.04)**: Docker 컨테이너 4개로 실행한다. frontend는 Next.js 서버로 화면을 제공하고 Caddy로 HTTPS와 경로별 프록시를 맡으며, auth는 회원가입 · 가입 이메일 인증 · 로그인 · 비밀번호와 인증 세션, backend는 강연 · 질문 · 필기 · 관리 요청과 권한 확인 · 실시간 연결, worker는 오래 걸리는 작업과 메일 발송을 맡는다. backend와 worker는 같은 코드와 이미지에서 실행 명령만 달리하고, auth는 별도 실행 단위다. 인증을 분리해 비밀번호 해시와 인증 코드 검증값은 auth만 읽고, backend는 세션 상태만 확인하는 제한된 조회 뷰를 쓴다. 데이터는 모두 같은 RDS에 두며 서비스별로 DB를 나누지는 않는다.
- **서비스 DB(AWS RDS for PostgreSQL 16 + pgvector)**: 서비스 데이터, 작업 상태, 검색용 벡터와 키워드 색인, 학습서버 레지스트리 복사본을 저장한다. 같은 VPC의 EC2에서만 접속한다. 교안 원본 파일은 S3에 둔다.
- **AI학습서버(학과 서버)**: 판정 모델의 데이터셋 관리 · 학습 · 평가 · 배포와 판정 추론을 맡는다(2.3). 서비스 서버와는 EC2 호스트에서 실행하는 SSH 터널로만 연결한다.

### 6.1.2 비동기 작업과 실시간 전달

오래 걸리는 처리(교안 처리, 질문 판정과 답변, 요약 노트, 메일 발송, 파기, 학습서버 연계)는 모두 작업(jobs)으로 처리한다.

1. backend는 요청을 검증한 뒤 업무 데이터와 작업 행을 하나의 트랜잭션으로 저장하고 202(접수)로 응답한다.
2. worker는 실행할 작업을 행 잠금으로 점유하고 점유 기한(lease)을 갱신하면서 실행한다. 결과는 점유 표식이 일치할 때만 저장해, 기한이 지나 다른 worker가 다시 맡은 작업의 결과가 겹치지 않게 한다.
3. 실패한 작업은 정해진 횟수까지 다시 시도하고, 끝내 실패하면 실패 상태와 오류 코드를 남긴다.
4. 질문 판정과 발화 색인은 교안 처리 · 요약보다 먼저 처리하고, 작업 종류별로 동시 실행 수를 따로 둔다.

실시간 전달은 DB 이벤트를 거친다. worker는 결과와 전달 이벤트(ws_events)를 함께 저장하고 PostgreSQL 알림(NOTIFY)으로 이벤트 번호만 backend에 알린다. backend는 이벤트를 읽어 받는 사람의 현재 권한을 확인한 뒤 해당 WebSocket으로 보낸다. 알림이 빠져도 이벤트 번호 이후를 다시 읽어 보완한다. 답변이 작성되는 동안의 글자 조각(answer.delta)은 임시 이벤트이며, 답변이 확정되거나 버려지면 지운다. 재접속한 화면은 임시 조각을 복원하지 않고 확정된 답변을 REST로 다시 받는다. 음성 프레임은 DB나 이벤트에 저장하지 않는다.

학습은 worker가 직접 실행하지 않는다. worker는 학습서버에 학습을 요청하고(7.4.7) 받은 작업 번호로 진행 상태(7.4.8)를 주기적으로 조회해 서비스 DB의 복사본을 갱신한다.

### 6.1.4 질문 처리와 판정

[그림: 질문 상태 전이 — 다시 그림]

질문은 다음 상태를 거친다.

- **QUEUED → PROCESSING**: worker가 질문 작업을 맡으면 질문자 화면에 "근거를 찾는 중" 진행 상태를 보낸다.
- **판정**: 같은 강연의 교안 · 발화에서 근거 후보를 최대 20개 찾는다. 후보가 없으면 근거 부족으로 이관한다. 서빙 모드가 CUSTOM이면 판정 추론을 호출하고, 최고 점수가 τ 이상이면 답변 단계로, 미만이면 이관한다. 800 ms 안에 응답이 없거나 오류가 나면 그 질문만 LLM_ONLY로 판정한다. 관리자가 서빙 모드를 LLM_ONLY로 바꾼 동안에는 모든 질문을 LLM_ONLY로 판정한다.
- **답변 작성**: 질문자 화면에 "답변을 작성하는 중" 상태를 보내고 Sonnet 답변을 글자 조각으로 전달한다. Sonnet이 첫 출력에서 근거가 부족하다고 판단하면 조각을 버리고 이관한다.
- **확정**: 답변 속 인용 번호가 넘겨준 근거 목록에 있는지 서버 코드로 대조하고, 유효한 인용이 하나 이상이면 답변을 저장해 **AI_ANSWERED**로 바꾼다. 유효한 인용이 없으면 이관한다.
- **이관(ESCALATED)**: 공개 목록에 올라가고 강연자 대시보드에 전달된다. 강연자가 구두로 답하고 완료를 누르면 **COMPLETED**가 된다. 강연자가 AI 답변을 철회해도 ESCALATED로 바뀐다.

질문마다 판정 경로(CUSTOM / 질문별 LLM_ONLY / 관리자 고정 LLM_ONLY), 후보별 점수와 순위, 실제 적용된 모델 버전 · τ(또는 τ_LLM · 모델 ID · 프롬프트 버전), 단계별 지연 시간을 판정 기록(decision_snapshot)에 남긴다. 서빙 설정의 원본은 학습서버이며, 판정 기록에는 계획된 값이 아니라 호출 때 실제로 적용된 값을 남긴다.

### 6.1.5 공용 검색 모듈

교안 청킹(R1), 확정 발화의 30초 청킹(R2), 하이브리드 검색(R3)을 화면 · 인증 · 작업 큐와 분리한 공용 패키지(retrieval)로 만든다. 서비스 worker와 학과 서버의 학습 데이터 생성이 같은 패키지와 같은 검색 설정을 쓴다.

- **키워드 색인**: 교안 · 발화 · 질문을 한국어 형태소 분석기 Kiwi로 나누고, 영어 용어는 소문자로 바꿔 그대로 둔 뒤 PostgreSQL 전문 검색(tsvector, simple 설정)으로 색인 · 검색한다. 조사가 붙은 한국어 단어("역전파는")도 같은 단어("역전파")로 찾기 위해서다.
- **벡터 색인**: Gemini Embedding 2(768차원) 벡터를 pgvector HNSW 색인으로 검색한다.
- **결합**: 벡터 검색 20개와 키워드 검색 20개를 RRF로 합쳐 상위 20개를 근거 후보로 쓴다. 항상 같은 강연 안에서만 검색한다.
- **검색 설정 버전(retrieval_config_version)**: 청킹 규칙 · 임베딩 모델과 차원 · 형태소 분석기 버전 · 결합 방식 · 후보 수(20) · 코드 버전을 하나로 묶은 불변 버전이다. 학습 데이터 레지스트리와 서비스 판정 기록에 함께 남긴다.
- AI Hub 데이터는 이 모듈의 외부 임베딩 경로를 쓰지 않고 학과 서버 안에서만 처리한다.

### 6.1.6 평가용 강의 판정

평가용 강의(검증 강좌 6.0001, 시험 강좌 6.172, 자체 녹음 강의)로 연 강연의 피드백이 학습셋에 들어가지 않도록, 강연마다 평가용 강의인지 판정한다(3.3.4).

1. 학습서버는 평가용 강의의 교안을 서비스와 같은 방식으로 나눈 평가용 교안 조각 목록(es-vN)을 만든다.
2. worker는 교안 처리를 시작할 때 목록 버전을 확인하고, 바뀌었을 때만 학습서버 API(7.4.28)로 받아 서비스 DB(eval_reference_chunks)에 저장한다.
3. 교안 처리가 끝나면 강연 교안 조각마다 평가용 조각과의 겹침을 계산한다. 텍스트를 정규화(NFKC, 영문 소문자, 문장부호를 공백으로, 연속 공백 정리)한 뒤 연속 5단어 묶음 집합을 만들고, 겹침 비율은 공통 묶음 수를 강연 교안 조각의 묶음 수로 나눈 값이다. 5단어보다 짧은 조각은 정규화한 전체 문장이 같은지로 본다.
4. 80% 이상 겹치는 조각이 강연 교안 조각의 30% 이상이면 강연을 평가용 강의(is_eval_lecture)로 표시하고 라벨 후보를 만들지 않는다. 강연 중 교안이 추가되면 다시 검사하고, 새로 평가용으로 판정되면 그 강연의 미병합 후보를 지운다.
5. 목록을 아직 받지 못했거나 검색 설정 버전이 맞지 않으면 검사 상태를 대기(PENDING)로 두고, 검사가 끝날 때까지 그 강연의 후보 생성을 미룬다.
6. 교안 없이 진행하는 평가용 강의는 관리자가 강연 시작 전에 평가용 강의로 표시한다(API-48).

같은 계산 함수를 학습서버의 병합 전 겹침 검사(6.4.3)에도 쓴다.

1. 방문자가 이메일 · 비밀번호(8~20자, 영문 · 숫자 각 1자 이상) · 표시 이름과 동의를 제출하면(API-01) Caddy가 auth로 전달한다. 가입 화면의 필수 동의 3개(이용약관 · 개인정보 수집 · 이용 · 질문 · 답변 기록 보관)는 SERVICE 동의 하나로, AI 개선을 위한 익명 활용은 TRAINING(선택)으로 보낸다. auth는 이메일 중복과 필수 동의를 확인하고, 인증 대기(PENDING_VERIFICATION) 회원 · 비밀번호 해시 · 동의 이력 · 인증 기록(6자리 코드의 HMAC, 10분 만료) · 메일 발송 작업을 한 트랜잭션으로 저장한다. 로그인 쿠키는 주지 않는다. worker가 fastapi-mail로 인증 메일을 보낸다.
2. 방문자가 가입 화면에서 코드를 입력하면(API-03) auth는 인증 기록을 잠그고 만료 · 사용 여부 · 실패 횟수를 확인한다. 성공하면 email_verified_at을 기록하고 ACTIVE로 바꾼 뒤 로그인 화면으로 보낸다(자동 로그인하지 않음). 메일을 받지 못했으면 재발송(API-02)을 요청하며, 60초 간격 · 시간당 5회 안에서 새 코드를 보내고 이전 코드는 무효가 된다.
3. 이메일 인증은 가입 때 한 번만 한다. 로그인(API-04)에서 auth는 비밀번호와 ACTIVE · 인증 완료 여부를 확인하고 인증 세션을 만들어 HttpOnly 쿠키와 CSRF 토큰을 준다. 인증하지 않은 계정은 EMAIL_NOT_VERIFIED로 거부하고 인증 화면으로 안내한다. 정지된 계정은 ACCOUNT_SUSPENDED와 관리자가 남긴 정지 사유를 돌려주고, 화면은 "이용이 정지된 계정이에요. 사유: …"를 보여준다.
4. 화면을 새로고침하거나 주소로 바로 들어오면 브라우저는 CSRF 토큰 재발급(API-06)과 내 정보 조회(API-09)로 로그인 상태를 복구한다. 관리자 화면도 같다.
5. 로그아웃(API-05)하면 auth가 인증 세션을 폐기하고 폐기 이벤트를 남기며, backend가 이를 받아 연결된 WebSocket을 닫는다.

- 실패 시 동작: 메일 발송이 실패하면 worker가 만료 전까지 재시도하고, 끝내 실패하면 재발송을 안내한다. 24시간 안에 인증하지 않은 계정은 정리한다. auth가 응답하지 않으면 가입 · 인증 · 로그인은 503으로 실패하지만, 이미 로그인한 사용자의 강연 · 질문 기능은 backend가 계속 처리한다. 비밀번호 · 인증 코드 · 토큰은 로그에 남기지 않는다.

### 6.2.2 비밀번호 재설정

- 관련: UC-S02 / API-07 · 08
- 선행 조건: 이메일 인증을 마친 계정

[그림: 비밀번호 재설정 sequence diagram — 새로 그림]

1. 회원이 이메일을 입력해 재설정을 요청하면(API-07) auth는 가입 여부와 관계없이 같은 응답을 돌려준다. 인증을 마친 계정이면 1회용 재설정 토큰의 HMAC과 만료 시각(30분)을 저장하고 메일 발송 작업을 등록한다. worker가 재설정 링크를 보낸다.
2. 회원이 메일의 링크로 들어와 새 비밀번호를 제출하면(API-08) auth는 토큰을 확인하고 비밀번호를 바꾼 뒤 토큰을 사용 처리한다. 그 계정의 기존 인증 세션을 모두 폐기하고, backend가 폐기 이벤트로 WebSocket을 닫는다.

- 실패 시 동작: 만료되었거나 이미 쓴 토큰이면 거부하고 재요청을 안내한다. 가입 여부를 응답으로 알리지 않는다.

### 6.2.3 강연 생성 · 교안 업로드 · 전문용어 · QR 발급

- 관련: UC-S04 · S05 · S06 · S20 / API-13 · 16 · 17 · 21 · 22 · 23 · 24 · 25
- 선행 조건: 로그인한 회원

[그림 (a): 강연 생성 · 교안 처리 sequence diagram — 다시 그림]
[그림 (b): 전문용어 사전 · QR 재발급 · 강연 시작 sequence diagram — 다시 그림]

1. 회원이 강연명 · 시작 예정 일시 · 설명(선택)을 입력하면(API-13) backend는 계정의 SERVICE 동의를 확인하고, 계정에 학습 활용 동의가 없을 때만 선택 항목을 다시 보여준다. DRAFT 강연을 만들고 입장 URL과 입장 코드(영문 대문자 · 숫자 5자리)를 돌려준다. 화면은 이를 QR로 만들고, 강연자는 준비 화면 · 대시보드에서 언제든 QR을 크게 띄울 수 있다. 예정 일시는 표시용이며 그 시각에 자동으로 시작하지 않는다. 강연 정보는 DRAFT에서만 고친다(API-16).
2. 강연자가 교안(PDF · PPTX, 50 MiB 이하)을 올리면(API-21) backend는 확장자 · 파일 형식 · 크기를 확인해 S3에 원본을 저장하고 교안 처리 작업을 등록한다. 교안은 DRAFT와 LIVE에서 올릴 수 있다.
3. worker는 텍스트를 추출해 페이지 번호를 유지한 채 청킹하고, 임베딩 · 형태소 분석 키워드 색인 · 용어 추출을 한 뒤 READY로 바꾼다. 처리 단계(업로드 → 텍스트 추출 · 청킹 → 임베딩 · 색인 → 용어 추출)와 끝난 뒤의 쪽수 · 검색 조각 수가 화면에 실시간으로 표시된다(API-22). 이어서 평가용 강의 검사(6.1.6)를 한다.
4. 교안에서 뽑은 용어는 강연의 전문용어 사전에 남은 자리만큼 더해진다. 강연자는 시작 전에 용어를 직접 넣거나 지운다(API-25, 강연당 100개, 각 1~40자). 지운 자동 용어는 다시 넣지 않는다. 사전은 시작할 때 고정되어 STT 연결마다 용어 힌트로 쓰인다(6.2.5).
5. 강연자가 시작을 누르면(API-16) DRAFT에서 LIVE로 바뀐다. 교안이 없어도 시작할 수 있으며, 이때는 발화만 근거로 쓴다. 처리 중인 교안은 READY가 되는 대로 검색에 포함된다.
6. QR을 다시 발급하면(API-17) 입장 코드를 바꿔 이전 QR · 코드 · 링크를 무효로 하고, 이미 입장한 청중은 그대로 둔다. 바로 전 코드로 들어오면 "강연자가 입장 QR을 새로 발급했어요"로 안내한다. 종료된 강연은 재발급하지 않는다.
7. 교안 삭제(API-24)는 DRAFT와 ENDED에서만 한다. 강연 중에는 이미 나간 답변의 근거가 사라지지 않도록 막는다.

- 실패 시 동작: 텍스트가 없는 스캔 PDF나 손상된 파일은 FAILED로 표시하고 교체(삭제 후 새 파일 업로드)를 안내한다. 임베딩 · 색인처럼 처리 중에 실패한 교안은 같은 원본으로 다시 처리한다(API-23). 교안이 처리 중이거나 실패한 채로 시작하면 화면은 "AI가 교안을 근거로 쓰지 못해 더 많은 질문이 강연자에게 넘어올 수 있어요"를 확인받고, 강연은 그대로 시작할 수 있다.

### 6.2.4 QR 입장(회원 · 게스트)

- 관련: UC-S13 / API-18 · 19 · 20
- 선행 조건: 유효한 QR · 입장 코드

[그림: QR 입장 sequence diagram — 다시 그림]

1. 청중이 QR을 찍거나 입장 코드를 입력하면 화면은 강연 확인(API-18)으로 강연명 · 강연자 · 예정 일시 · 설명 · 정원 상태를 보여주고 "회원으로 입장"과 "게스트로 입장"을 고르게 한다. 게스트 쪽에는 "강연이 끝나면 내 질문과 답변을 다시 볼 수 없습니다"를 함께 표시한다. 회원으로 입장을 고르면 로그인한 뒤 같은 입장 요청을 이어서 보낸다. 화면은 강연 상태를 확인한다.
   - DRAFT: 입장할 수 있고 "곧 시작합니다" 대기 화면을 보여준다. 질문은 막는다. 강연이 시작되면 WebSocket으로 화면이 바뀐다.
   - LIVE: 입장하고 질문할 수 있다.
   - ENDED: 입장을 거부한다. 회원이면 내 보관함으로 안내한다.
2. 회원은 계정의 SERVICE 동의를 그대로 쓰고, 학습 활용 동의가 없을 때만 선택 항목을 보여준다. 게스트는 입장할 때마다 닉네임(1~20자)과 SERVICE(필수) · TRAINING(선택)을 제출하고, 선택하지 않은 항목은 false로 저장한다. 닉네임은 게스트 본인 화면에만 쓰고 질문 목록 · 강연자 화면에는 표시하지 않는다.
3. backend는 입장 코드, 강연 상태, 정원(청중 50명), 동의를 확인하고 참가자를 만든다(API-19). 이미 참가한 사람이 다시 들어오면 정원과 관계없이 기존 참가를 돌려준다. 참가자 수가 바뀌면 강연자 대시보드와 대기 화면에 실시간으로 반영한다. 게스트이면 auth 내부 API(INT-01)로 그 강연 전용 게스트 세션을 받아 쿠키로 전달한다. 회원은 기존 로그인 세션을 그대로 쓴다. 이후 브라우저는 WebSocket에 접속해 본인 채널과 공개 질문 목록을 받는다.

- 실패 시 동작: 없는 코드면 코드를 다시 확인하도록, 재발급으로 무효가 된 코드면 새 QR로 들어오도록 안내한다. 같은 IP에서 잘못된 코드가 15분에 20번을 넘으면 15분 동안 입장 코드 확인을 거부한다. 정원이 찼으면 입장할 수 없다고 안내한다. auth가 응답하지 않아 게스트 세션을 받지 못하면 503으로 실패하며, 다시 시도하면 같은 참가자를 재사용한다.

### 6.2.5 실시간 음성 전송 · 일시정지 · 재연결

- 관련: UC-S08 · S21 / API-16 · 20, WebSocket audio · stt 이벤트
- 선행 조건: 강연자, LIVE, STT 동의, 브라우저 마이크 허용

[그림: 실시간 음성 전송 sequence diagram — 다시 그림]

1. 강연자가 음성 전송을 시작하면 화면은 이 강연의 STT 동의를 확인하고, 없으면 동의를 받는다(API-20). 동의는 강연마다 받는다.
2. 브라우저는 16 kHz 모노 음성을 100 ms 프레임으로 WebSocket에 보낸다. backend는 강연 소유권과 LIVE 상태를 확인한 뒤 스트림 번호와 프레임 순번을 관리하며 음성을 메모리에서 STT로 중계한다.
3. 인식 중간 결과는 상태 표시에만 쓰고, 확정된 발화만 DB에 저장한다. worker는 약 30초 단위로 모은 발화 청크를 임베딩 · 키워드 색인해 검색 가능 상태로 바꾼다. 발화 시점부터 검색 가능 시점까지 45초 이내를 목표로 한다.
4. 강연자가 일시정지하면 새 음성 입력을 막고 남은 확정 구간까지 처리한다. 이미 색인된 발화는 계속 검색에 쓴다.
5. 연결이 끊겼다가 다시 이어지면 스트림과 순번을 확인해 중복 저장을 막는다. STT의 10분 연결 제한에 맞춰 backend가 STT 연결을 자동으로 다시 연다. STT 연결마다 강연의 전문용어 사전(6.2.3)을 용어 힌트로 넣는다.

- 실패 시 동작: 메모리 버퍼(5초)를 넘겨 잃은 구간은 인식 누락으로 표시한다. 임베딩이 실패한 발화는 PENDING으로 남겨 재시도한다. 음성 원본은 디스크에 저장하지 않는다.

### 6.2.6 유사 질문 확인 · 공감

- 관련: UC-S14 · S17 / API-26 · 28 · 30 · 31
- 선행 조건: 강연 참가자

[그림: 유사 질문 확인 · 공감 sequence diagram — 다시 그림]

1. 청중이 질문을 입력하면 화면은 입력이 멈춘 뒤 유사 질문 검색을 요청한다(API-26). backend는 같은 강연의 공개 질문만 검색해 최대 3개와 공감 수를 돌려준다. 개인 답변을 받은 질문은 검색 대상이 아니며, 입력 중인 문장은 저장하지 않는다.
2. 청중이 기존 질문에 공감하면(API-30) backend는 인증 세션에서 참가자를 정하고, 공감 가능한 상태(LIVE 강연의 ESCALATED 질문)인지 확인한 뒤 공감을 저장한다. 같은 요청을 반복해도 공감 수는 한 번만 늘어난다. 공감 취소(API-31)는 본인 공감만 지운다. 바뀐 공감 수는 모든 참가자에게 실시간으로 전달된다.
3. 유사도만으로 질문을 자동 병합하거나 삭제하지 않는다. 청중이 공감을 고르면 새 질문을 만들지 않는 방식으로 중복을 줄인다.

### 6.2.7 질문 판정 · 개인 답변 · 공개 이관

- 관련: UC-S15 · S22 / API-27 · 29 · 38
- 선행 조건: LIVE 강연의 참가자, SERVICE 동의

[그림 (a): 질문 접수 · 판정 sequence diagram — 다시 그림]
[그림 (b): 답변 생성 · 확정 sequence diagram — 다시 그림]

1. 청중이 질문(1~200자)을 제출하면(API-27) backend는 참가 권한 · SERVICE 동의 · LIVE 상태 · 중복 요청 키를 확인하고 질문과 질문 작업을 한 트랜잭션으로 저장한다.
2. worker는 6.1.4의 순서로 처리한다. 질문자 화면에는 "근거를 찾는 중" → "답변을 작성하는 중" 진행 상태와 답변 글자가 실시간으로 표시된다.
3. 답변이 확정되면 질문자에게만 답변과 근거 위치("교안 p.9", "발화 21:05")를 보여준다. 강연자 대시보드의 AI 답변 검토 목록에도 올라간다. 인용 근거의 원문은 강연 원자료 보관 기간 안에서 확인할 수 있다(API-38).
4. 이관된 질문은 공개 목록에 올라가 모든 참가자와 강연자에게 전달된다. 공개 목록에는 작성자를 표시하지 않는다.
5. 판정을 통과했지만 Sonnet이 근거 부족으로 이관한 질문은, 질문자와 강연자가 모두 학습 활용에 동의했고 평가용 강의가 아니면 라벨 후보(SECOND_STAGE_INSUFFICIENT)로 저장한다. 판정 모델이 이관한 질문은 같은 조건에서 라벨 후보(AUTO_ESCALATED)로 저장한다.

- 실패 시 동작: 판정 추론이 800 ms를 넘기거나 실패하면 그 질문만 LLM_ONLY로 판정한다. LLM_ONLY와 답변 생성이 모두 실패하면 이관한다. 근거가 없으면 답변을 만들지 않고 이관한다.

### 6.2.8 강연자 검토 · 철회 · 답변 완료

- 관련: UC-S09 · S10 · S11 / API-28 · 32 · 33
- 선행 조건: 강연자(본인 강연), LIVE

[그림: 강연자 검토 · 철회 · 답변 완료 sequence diagram — 다시 그림]

1. 강연자가 대시보드를 열면(API-28) backend는 소유권을 확인하고, 이관 질문 목록(교안 페이지별 · 공감순)과 AI 답변 검토 목록을 돌려준다. 어느 목록에도 질문 작성자는 표시하지 않는다.
2. 강연자가 AI 답변을 철회하려면 사유를 하나 고른다(API-33): "답이 틀렸거나 근거가 부족함"(WRONG_OR_INSUFFICIENT) 또는 "중요해서 직접 한 번 더 설명"(EXPLAIN_AGAIN). backend는 질문 버전과 답변 상태(ACTIVE)를 확인한 뒤 답변 숨김, 질문 공개 이관, 감사 기록을 한 트랜잭션으로 처리하고 질문자에게 철회를 알린다.
3. 철회는 질문자와 강연자가 모두 학습 활용에 동의했고 평가용 강의가 아니면 라벨 후보(RETRACTED)가 된다. 기본 라벨은 사유에 따라 근거 부족 또는 답변 가능이며, 관리자 2인 검수에서 확정한다.
4. 강연자가 구두로 답한 이관 질문에 완료를 누르면(API-32) COMPLETED로 바뀌고 모든 참가자 화면에 반영된다. 잘못 눌렀으면 완료를 취소해 ESCALATED로 되돌린다.
5. 답변은 강연 중 구두로만 하므로 철회와 완료 표시 · 취소는 LIVE에서만 한다. 강연이 끝날 때 ESCALATED로 남은 질문은 그대로 강연 기록에 남는다.

### 6.2.9 강연 종료 · 요약 노트

- 관련: UC-S07 · S23 / API-16 · 37
- 선행 조건: LIVE 강연

[그림: 강연 종료 · 요약 노트 sequence diagram — 다시 그림]

1. 강연자가 종료를 누르거나(API-16), LIVE 시작 후 12시간이 지나거나, 관리자가 강제 종료하면(API-48) 강연을 ENDED로 바꾸고 종료 사유(HOST / AUTO_TIMEOUT / ADMIN)를 남긴다. 새 질문과 음성 입력을 막는다.
2. worker는 정리 작업으로 진행 중인 질문 처리와 마지막 발화 구간을 제한 시간 안에 마무리한다. 시간 안에 끝나지 않은 질문은 이관한다.
3. 정리 작업은 강연 통계(질문 · AI 답변 · 이관 · 답변 완료 · 철회 수, 공감 합계, 참가자 수, 교안 페이지별 질문 수)를 한 번 집계해 강연에 저장한다(6.2.14). 게스트 질문 내용을 지우기 전에 집계하므로 이후 정리 · 파기로 숫자가 바뀌지 않는다.
4. 정리가 끝나면 교안과 발화로 요약 노트를 한 번 만든다. 한 줄 요약 · 핵심 개념(용어와 설명) · 강조한 점 · 키워드로 나눠 저장한다. 개인 질문과 개인 답변은 요약에 넣지 않는다. 확정 발화가 1,000자 미만이면 요약을 만들지 않고 SKIPPED로 둔다. 요약의 인용을 검증한 뒤 저장하고 참여 회원과 강연자에게 알린다.
5. 게스트의 인증은 강연 종료 때 끝나고, 게스트 화면은 종료 안내만 보여준다. 정리 작업은 게스트 닉네임과, 학습 활용에 동의하지 않은 게스트의 개인 질문 · AI 답변 내용을 지운다(6.2.11).

- 실패 시 동작: 요약 생성이 실패하면 정해진 횟수까지 재시도하고, 끝내 실패하면 실패 상태를 보여준다. 조회할 때마다 새로 만들지 않는다.

### 6.2.10 내 보관함 · 필기

- 관련: UC-S18 · S19 / API-12 · 14 · 28 · 29 · 35 · 36 · 37 · 40
- 선행 조건: 로그인한 회원

[그림: 내 보관함 · 필기 sequence diagram — 새로 그림]

1. 강연 중 회원 청중은 공개 질문 옆의 연필 버튼으로 필기를 쓴다(API-35). 질문 하나에 한 사람당 필기 하나이며 1,000자까지 쓰고 언제든 고친다. backend는 필기와 함께 질문 문장을 복사해 저장한다. 필기는 쓴 사람만 보며, 강연자 화면 · 요약 노트 · 학습 데이터에 쓰지 않는다. 게스트 화면에는 연필 버튼이 없다.
2. 회원이 내 보관함을 열면(API-14, joined) 청중으로 참여한 강연 목록이 강연명 · 강연자 · 날짜 · 내 질문 수 · 요약 노트 여부와 함께 나온다. 본인이 연 강연은 보관함이 아니라 내 강연에 있다. 강연명 · 강연자 이름으로 검색할 수 있다.
3. 강연을 고르면 세 탭을 보여준다.
   - 요약 노트(API-37)
   - 내 질문(API-12): 내 질문, AI 답변과 근거 위치, 처리 상태
   - 전체 질문(API-28): 그 강연의 공개 질문 전체와 공감 수 · 답변 완료 여부, 내가 공감한 질문 배지, 내 필기. 보관함에서도 필기를 쓰고 고칠 수 있다.
4. 회원은 질문 단위로 내 기록을 지우거나, 보관함에서 강연 하나를 통째로 지운다(API-40, ARCHIVE). 강연을 지우면 그 강연의 내 질문 · 내 답변 · 내 필기가 삭제되고 보관함 목록에서 빠진다.

보관 기간은 6.2.11을 따른다.

### 6.2.11 동의 철회 · 삭제 · 보관 기간

- 관련: UC-S03 · S12 / API-11 · 20 · 40 · 41
- 선행 조건: 대상의 소유자

[그림: 동의 철회 · 삭제 · 보관 기간 sequence diagram — 다시 그림]

데이터는 세 묶음으로 나누어 보관한다.

표: 데이터 보관 범위

| 묶음 | 내용 | 보관 기간 |
|---|---|---|
| 게스트 닉네임 · 개인 질문(학습 미동의) | 게스트 닉네임, 학습 활용에 동의하지 않은 게스트의 개인 질문과 AI 답변 내용 | 강연 종료 정리 때 |
| 강연 원자료 | 교안 원본 · 교안 조각 · 발화 · 벡터 · 키워드 색인, 학습 활용에 동의한 게스트의 개인 질문과 AI 답변, 게스트 참가 정보, 미병합 라벨 후보 | 강연 종료 후 90일 |
| 강연 기록 | 강연 제목 · 날짜 · 강연자 표시명, 요약 노트, 공개 질문 전체(내용 · 공감 수 · 답변 완료 여부) | 참여 회원 중 한 명이라도 보관함에 이 강연을 남겨 둔 동안 |
| 회원 개인 기록 | 내 질문, 내 AI 답변(근거 위치 텍스트 포함), 내 필기, 내 공감 표시, 내 1:1 문의 | 회원이 지우거나 탈퇴할 때까지 |

1. **게스트 개인 질문 정리**: 게스트는 강연이 끝나면 자기 질문을 다시 볼 수 없고 강연자의 철회 · 검토도 강연 중에만 하므로, 게스트 닉네임과, 학습 활용에 동의하지 않은 게스트의 개인 질문 · AI 답변 내용(질문 문장 · 답변 · 인용)은 종료 정리 때 지운다. 처리 상태 · 판정 경로 · 응답 시간 같은 내용 없는 기록은 운영 지표(6.3.5)를 위해 남긴다. 학습 활용에 동의한 게스트의 개인 질문은 라벨 후보 검수 · 병합을 위해 90일까지 둔다.
2. **보관 기간 파기**: worker는 매일 종료 후 90일이 지난 강연의 원자료를 파기하고 강연 상태를 PURGED로 바꾼다. 게스트 참가 정보가 지워지면서 게스트가 쓴 공개 질문은 DB에서도 작성자를 알 수 없게 된다. 답변의 근거 위치는 텍스트로 남아 있어 보관함에서 계속 보인다.
3. **강연자 삭제**(API-40, SESSION): 강연 원자료를 즉시 파기하고 강연자의 내 강연 목록에서 뺀다. 강연 기록은 참여 회원의 보관함을 위해 남긴다.
4. **강연 기록 삭제**: 참여 회원이 모두 보관함에서 그 강연을 지우거나 탈퇴하면 강연 기록을 삭제한다. 강연자도 탈퇴했고 참여 회원도 없으면 바로 삭제한다.
5. **탈퇴**(API-40, ACCOUNT): 최근 10분 안에 로그인한 상태에서만 받는다. 본인이 진행 중인 강연이 있으면 받지 않고 강연 종료를 먼저 안내한다. 접근을 먼저 막고 회원 개인 기록과 미병합 라벨 후보를 지운다. 강연자로 만든 강연은 3과 같이 처리한다. 그 회원이 쓴 공개 질문은 작성자 연결을 끊고 강연 기록에 남긴다.
6. **학습 동의 철회**(API-11, API-20): 새 동의 이력을 저장하고 이후 라벨 후보를 만들지 않는다. 이미 만든 미병합 후보는 지운다. 학습서버로 보내는 중인 후보는 병합 요청 번호로 실제 병합 여부를 확인한 뒤 처리한다. 병합된 데이터는 원래 질문과 연결이 끊긴 익명 데이터라 데이터셋과 학습된 모델은 바꾸지 않으며, 동의 화면에 이 범위를 안내한다.
7. **삭제 처리 순서**: 접근 차단 → 진행 중 작업 결과 저장 차단 → 미병합 후보 · 임시 이벤트 정리 → S3 객체 삭제 → DB 행 · 벡터 · 색인 삭제 → 확인. 진행 상태는 작업 조회(API-41)로 본다.

- 실패 시 동작: S3 삭제가 실패하면 접근을 막은 채 재시도한다. 음성 원본은 처음부터 저장하지 않는다.

### 6.2.12 계정 관리

- 관련: UC-S03 / API-06 · 09 · 10 · 11
- 선행 조건: 로그인한 회원

[그림: 계정 관리 sequence diagram — 다시 그림]

1. 계정 화면을 열면 auth가 내 정보와 계정 단위 동의 상태를 돌려준다(API-09). 새로고침으로 화면의 CSRF 토큰이 사라졌으면 같은 출처에서만 재발급받는다(API-06).
2. 표시명이나 비밀번호를 바꾸면(API-10) 형식을 확인하고, 비밀번호 변경은 현재 비밀번호를 확인한다. 비밀번호가 바뀌면 다른 기기의 인증 세션과 WebSocket을 모두 폐기하고 현재 브라우저에 새 인증 정보를 준다.

4. 이메일 변경과 게스트 기록의 회원 계정 이전은 제공하지 않는다.

### 6.2.13 청중의 AI 답변 평가

- 관련: UC-S16 · D06 / API-29 · 34
- 선행 조건: 질문 작성자, ACTIVE 답변

[그림: 청중 평가 sequence diagram — 다시 그림]

1. 청중이 내 질문의 AI 답변에 "도움됨" 또는 "부족해요"를 누르면(API-34) backend는 작성자 · 답변 상태를 확인하고 평가를 저장한다. 같은 요청을 반복해도 평가와 후보가 중복되지 않는다.
2. 평가는 학습 동의와 관계없이 쓸 수 있다. 질문자와 강연자가 모두 학습 활용에 동의했고 평가용 강의가 아니면 라벨 후보를 만든다. "도움됨"은 기본 라벨 답변 가능(AUDIENCE_HELPFUL), "부족해요"는 기본 라벨 없음(AUDIENCE_UNHELPFUL)이며, 관리자 2인 검수에서 확정한다.
3. 평가만으로 답변을 공개하거나 철회하지 않는다.

### 6.2.14 강연 리포트 · 통계

- 관련: UC-S12 / API-14 · 28 · 37 · 39 · 40
- 선행 조건: 강연자(본인 강연), ENDED · PURGED

[그림: 강연 리포트 · 통계 sequence diagram — 새로 그림]

1. 강연자가 지난 강연을 고르면 리포트를 요약 노트(API-37) · 공개 질문(API-28) · 통계(API-39) 탭으로 보여준다. 리포트 머리에는 종료 사유(직접 종료 / 12시간 자동 종료 / 관리자 종료), 일시, 청중 수를 보여준다.
2. 통계는 종료 처리(6.2.9) 때 저장한 값을 그대로 보여준다. 질문 원문과 작성자는 통계에 넣지 않는다. 통계 화면은 F11-1(Should)이다.
3. 강연자는 리포트에서 교안을 지우거나(API-24) 강연 원자료를 지운다(API-40, SESSION). 원자료를 지우면 강연자의 리포트에서는 바로 사라지고, 보관함에 이 강연을 둔 회원이 있으면 강연 기록(제목 · 일시 · 요약 노트 · 공개 질문)과 그 회원의 개인 기록은 남는다(6.2.11). 질문 하나를 지우는 것은 작성자 본인만 한다.

### 6.2.15 공지 · 1:1 문의(회원)

- 관련: UC-S03 / API-42 · 43 · 44
- 선행 조건: 로그인한 회원

[그림: 공지 · 1:1 문의 sequence diagram — 새로 그림]

1. 회원은 내 정보 화면에서 공지 목록(API-42)을 본다. 마지막으로 본 뒤 새 공지가 있으면 표시를 붙인다.
2. 회원이 제목과 내용으로 1:1 문의를 남기면(API-43) 답변 대기로 저장된다. 회원은 내 문의 목록(API-44)에서 관리자 답변을 확인한다. 공지 · 문의는 F13-1(Should)이다.

## 6.3 관리자 기능설계 (Sequence Diagram)

관리자는 서버에서 생성한 ADMIN 계정으로 로그인 API(API-04)를 써서 로그인하며, backend는 모든 관리자 요청에서 현재 계정의 ADMIN 권한을 확인한다. 웹 화면에서는 관리자 계정을 만들거나 역할을 바꿀 수 없다.

### 6.3.1 회원 · 강연 관리와 강제 종료

- 관련: UC-S24 · S25 · S26 / API-45 · 46 · 47 · 48
- 선행 조건: ADMIN

[그림: 회원 · 강연 관리 sequence diagram — 다시 그림]

1. 회원 · 강연 목록(API-45, API-47)에는 운영에 필요한 식별자와 상태만 보여주고 질문 원문은 넣지 않는다.
2. 계정을 정지하면(API-46) backend는 사유와 함께 상태 변경 · 감사 기록 · 세션 폐기 작업(AUTH_REVOKE)을 한 트랜잭션으로 저장한다. 상태가 바뀌는 즉시 권한 확인에서 접근이 막히고, worker가 auth 내부 API(INT-02)로 인증 세션을 폐기해 WebSocket도 닫힌다. 정지 사유는 로그인 화면에 보여준다. 그 계정이 강연자로 진행 중인 LIVE 강연은 강제 종료하고(end_reason = ADMIN), 청중으로 참가 중이던 강연에서는 세션 폐기로 바로 나가진다. 아직 시작하지 않은 강연은 그대로 둔다. 정지를 풀 때는 남은 세션을 모두 폐기한 뒤 ACTIVE로 바꾸므로 다시 로그인해야 한다. 마지막 활성 관리자 계정은 정지할 수 없다.
3. 강제 종료(API-48)는 진행 중(LIVE) 강연에만 하며, 버전을 확인하고 6.2.9의 종료 처리를 한다. 아직 시작하지 않은(DRAFT) 강연은 강제 종료 대상이 아니다. 교안 없이 진행할 평가용 강의는 시작 전에 평가용 강의로 표시하며, 한 번 표시하면 되돌리지 않는다.

### 6.3.2 라벨 후보 검수와 데이터셋 병합

- 관련: UC-D07 · D08 / API-53 · 54 · 55 · 56
- 선행 조건: ADMIN

[그림: 라벨 후보 검수와 병합 sequence diagram — 다시 그림]

1. 후보 목록(API-53)은 조회할 때마다 질문자 · 강연자의 현재 학습 동의와 평가용 강의 여부를 다시 확인한 후보만 보여준다. 판정 모델이 이관한 후보는 판정 당시 모델 버전별로 임계값에 가까운 순서로 정렬한다. 계정 식별자는 보여주지 않는다.
2. 검수 화면은 정제한 질문, 기본 라벨, 그 질문의 검색 후보 목록을 보여준다. 두 관리자가 서로의 결과를 보지 않고 각자 라벨을 고른다(API-54). 판정 모델 이관 후보를 답변 가능으로 고를 때는 검색 후보 중 정답 근거를 반드시 고른다. 두 사람의 라벨과 근거가 같으면 승인, 다르면 불일치로 다시 검수한다. 후보 중에 정답 근거가 없으면 제외한다.
3. 관리자가 기준 데이터셋 버전과 승인 후보로 병합을 요청하면(API-55) worker는 동의를 다시 확인하고 정제한 질문-근거 쌍을 학습서버 병합 API(7.4.5)로 보낸다. 학습서버는 6.4.3대로 학습셋에만 병합해 새 버전을 만든다.
4. 병합 완료를 확인하면 서비스 쪽 후보와 원래 질문의 연결, 전송용 대응표를 지우고 새 데이터셋 버전의 통계만 복사본에 남긴다(API-56). 병합 요청 시점 이전에 생긴, 검수하지 않은 자동 이관 후보도 함께 지운다.

### 6.3.3 학습 · 재학습 실행과 중단

- 관련: UC-L04 · L05 / API-57 · 58 · 59 · 61
- 선행 조건: ADMIN, 승인된 데이터셋 버전

[그림: 학습 실행과 중단 sequence diagram — 다시 그림]

1. 관리자가 데이터셋 버전과 허용된 학습 설정(에폭 · 배치 · 학습률)을 고르면(API-57) backend는 진행 중(LIVE)인 강연이 있는지 확인한다. 학습은 판정 추론과 같은 GPU를 쓰므로 강연 중에 돌리면 판정이 800 ms를 넘겨 LLM_ONLY로 빠지는 질문이 늘기 때문에, LIVE 강연이 있으면 LIVE_SESSION_IN_PROGRESS로 거부하고 화면은 "진행 중인 강연이 끝난 뒤 실행할 수 있어요"를 보여준다. AI 담당자가 학과 서버에서 직접 학습 · 평가 · 변환을 실행할 때도 진행 중인 강연이 없는 시간에만 한다. 통과하면 학습 요청 이력을 만든다. worker는 이 요청 번호를 학습서버 요청 번호로 써서 자동 연결 학습(7.4.7)을 요청한다. 같은 요청이 다시 가도 학습은 한 번만 돈다.
2. 학습서버는 학습 → fp16 변환 → 평가 → 등록 → 서빙 버전 비교를 이어서 실행한다(6.4.5). worker는 진행 상태(7.4.8)를 주기적으로 조회해 단계 · 학습 곡선 · 지표 · 등록 버전을 복사본에 갱신하고, 관리자 화면에 진행률과 학습 곡선을 보여준다(API-58, API-61).
3. 등록 조건이나 fp16 하락 기준을 넘지 못하면 HELD와 사유가 표시되고 이후 단계는 실행하지 않는다.
4. 관리자가 중단하면(API-59) 학습서버 중단 API(7.4.9)로 전달해 남은 단계까지 취소한다. 이미 끝난 작업은 중단할 수 없다. 학습이 끝나도 자동으로 배포하지 않는다.

### 6.3.4 서빙 전환 · 롤백 · LLM_ONLY

- 관련: UC-L06 · L07 / API-60 · 62 · 63
- 선행 조건: ADMIN

[그림: 서빙 전환 · 롤백 sequence diagram — 다시 그림]

1. 모델 버전 목록(API-60)에는 버전별 지표, 배포 가능 여부(deployable), 현재 서빙 여부(serving), 서빙 이력(served_before)을 보여준다.
2. **새 버전 전환**: 한 번도 서빙하지 않은 버전은 배포 가능 버전만 고를 수 있다. backend는 요청 이력을 남기고 학습서버 전환 API(7.4.22)로 보낸다. 학습서버가 그 시점의 서빙 버전과 다시 비교해 미달이면 거부한다.
3. **롤백**: 서빙한 적 있는 버전과 LLM_ONLY만 고를 수 있다. 학습서버 롤백 API(7.4.23)로 보내며 성능 비교 없이 바꾼다.
4. 전환이 끝나면 worker는 서빙 설정 조회(7.4.21)로 실제 버전 · τ · τ_LLM을 받아 복사본을 갱신하고, 이후 판정에 쓴다(API-63).
5. 판정 추론 시간 초과로 질문 하나가 LLM_ONLY로 처리된 것은 서빙 설정을 바꾸지 않고 그 질문의 판정 기록에만 남긴다.

- 관련: UC-S27 / API-64 · 65, API-53~63

[그림: 운영 지표와 피드백 순환 sequence diagram — 다시 그림]

1. 관리자가 기간과 집계 단위(일 · 강연)를 고르면(API-64) 질문 수, AI 답변 비중, 이관 비율, 응답 시간(진행 상태 표시 · 첫 글자 · 최종 확정), 발화 반영 지연, 대체 판정(LLM_ONLY) 횟수, 철회 · 청중 평가 건수, 실패 작업, 외부 API 호출 수와 추정 비용을 보여준다. 표본이 없으면 0이 아니라 값 없음으로 표시한다.

3. 운영 질문에는 검수된 정답이 없으므로 운영 지표로 오답 즉답률 · 정확도를 표시하지 않는다. 판정 모델의 성능은 평가셋 결과(API-61)로만 본다.
4. 철회나 대체 판정이 늘면 관리자는 라벨 후보 검수(6.3.2) → 재학습(6.3.3) → 버전 비교 · 전환(6.3.4)으로 이어서 개선한다. 모든 운영 변경에는 실행한 관리자와 사유를 감사 기록으로 남긴다.

### 6.4.1 데이터셋 버전 등록 (T-01)

3장에서 만든 라벨 데이터셋을 학습에 쓸 수 있도록 검증하고 버전으로 등록한다.

[그림: 데이터셋 버전 등록 sequence diagram — 다시 그림]

AI 담당자가 학과 서버의 데이터셋 폴더(train.jsonl · validation.jsonl · test.jsonl)와 생성 스크립트 버전 · 검색 설정 버전으로 등록을 요청하면, 학습서버가 파일을 읽어 검사한다. 학습셋은 3.3.3의 학습 필드를, 검증 · 시험셋은 평가 필드(후보 20개 이하 · gold_evidence_ids · gold_in_candidates)를 본다. 정답 근거는 후보 안에 있어야 하고, 같은 강좌가 두 분할에 있으면 안 되며, 검증 · 시험셋에는 AI Hub 행이 없어야 하고, 시험셋은 사람 라벨만 있어야 한다. 하나라도 어긋나면 오류 행 목록과 함께 601을 돌려주고 장애를 기록한다. 통과하면 분할별 질문 · 쌍 수와 라벨 · 출처 분포를 계산해 /data/easyq/datasets/ds-vN/에 저장하고 레지스트리에 등록한다. 검증 · 시험셋 내용이 바뀌면 검증 · 시험셋 버전(val-vN · test-vN)과 평가용 교안 조각 목록(es-vN)도 새로 만든다. 등록한 버전은 수정하지 않는다.

### 6.4.2 데이터셋 · 모델 · 작업 조회 (T-02, T-15, T-17)

관리자 웹의 데이터셋 현황(F9-4) · 학습 결과(F9-5) 화면을 채운다.

[그림: 데이터셋 · 모델 · 작업 조회 sequence diagram — 다시 그림]

화면을 열면 backend가 데이터셋 목록, 모델 버전 목록, 실행 중인 작업을 차례로 조회해 한 화면에 보여준다. 모델 버전 목록에는 서빙 여부와 서빙 이력이 함께 온다. 모델 하나를 고르면 상세 API가 ROC 곡선을 그릴 점 목록과 manifest를 돌려주어 관리자 웹이 곡선을 그린다.

### 6.4.3 검수 라벨 병합 (T-03)

관리자 검수를 마친 라벨 후보를 재학습 데이터로 만든다.

[그림: 검수 라벨 병합 sequence diagram — 다시 그림]

backend가 관리자 2인 검수를 마친 후보의 정제본(question_text · evidence_id · evidence_type · evidence_text · page_no · start_ms · end_ms · course_id)과 확정 라벨을 병합 요청 번호와 함께 보낸다. 학습서버는 다음 순서로 처리한 뒤 기준 버전의 학습셋에만 더해 새 버전을 만든다. 검증 · 시험셋은 그대로 두어 재학습 전후 모델을 같은 기준으로 비교한다. 같은 요청 번호가 다시 오면 새 버전을 만들지 않고 앞서 만든 결과를 돌려준다.

1. **개인정보 재마스킹**: backend가 정제본을 만들 때 1차로 가린 것을 같은 규칙(전화번호 · 이메일 · 학번 형태 숫자열 → [MASK])으로 다시 검사한다. 정규식으로 잡기 어려운 사람 이름은 관리자 검수 화면에서 확인해 제외한다. 가린 뒤 의미를 잃은 라벨은 제외한다.
2. **평가용 강의 겹침 제외**: 근거 텍스트를 평가용 교안 조각 · 검증 · 시험셋 근거와, 질문 텍스트를 검증 · 시험셋 질문과 비교해 5단어 묶음이 80% 이상 겹치면 뺀다. 계산은 6.1.6과 같은 함수(분모는 피드백 쪽 텍스트)를 쓴다.
3. **학습 전용 ID 교체**: evidence_id · course_id를 학습 전용 ID로 바꾸고 서비스 ID와의 대응표를 남기지 않는다.

병합된 행은 source = FEEDBACK, question_source = FEEDBACK, label_source = HUMAN이다. 응답에는 추가 · 겹침 제외 · 마스킹 · 제외 건수를 돌려준다.

### 6.4.4 데이터 재수집 (T-04)

학습 데이터가 부족한 주제의 공개 강의 자료를 추가로 모은다.

[그림: 데이터 재수집 sequence diagram — 다시 그림]

AI 담당자가 출처 목록을 주면 학습서버가 수집 작업을 등록하고 바로 작업 번호를 돌려준다. 작업 실행기는 자료를 모으면서 라이선스를 확인하고, 라이선스가 불분명하거나 접속에 실패한 항목은 제외하고 장애로 남긴다(F8-1). 수집 결과는 원천 데이터(/data/easyq/raw/)로만 저장하며, 라벨링을 거쳐 6.4.1로 등록해야 학습에 쓸 수 있다.

### 6.4.5 판정 모델 학습 · 재학습 실행과 진행 조회 (T-05, T-06)

데이터셋 버전으로 판정 모델을 학습하고 진행 상황을 보여준다. 재학습(F12-3)은 같은 흐름에 새 데이터셋 버전을 넣는 것이다.

[그림: 학습 · 재학습 실행 sequence diagram — 다시 그림]

학습서버는 데이터셋과 파라미터를 확인하고, 다른 학습 · 평가 · 변환 작업이 GPU를 쓰고 있으면 609를 돌려준다. 판정 추론 프로세스는 GPU에 상주하므로, 학습 배치 크기는 추론 프로세스가 쓰는 메모리를 뺀 GPU 메모리에 맞춘다. backend가 보낸 요청 번호가 이미 받은 값이면 기존 작업 번호를 돌려준다. 작업 실행기는 에폭마다 검증셋 질문 단위 ROC-AUC와 손실을 기록하고, 끝나면 최적 체크포인트를 저장한다. 이어서 같은 작업이 fp16 변환(6.4.10) → 평가(6.4.8) → 등록 조건 확인 → 등록 → 서빙 버전과 비교(6.4.9)로 이어진다. fp16 하락이 0.01을 넘으면 precision_drop, 등록 조건(추론 시간 포함)을 넘지 못하면 below_target 사유로 HELD가 되고 이후 단계는 실행하지 않는다. backend는 이 작업 번호 하나로 단계 · 학습 곡선 · 평가 지표 · 등록 버전을 조회한다.

### 6.4.6 학습 작업 중단 (T-07)

잘못 시작했거나 학습 곡선이 나빠진 학습을 멈춘다.

[그림: 학습 작업 중단 sequence diagram — 다시 그림]

실행 중인 작업만 중단할 수 있고, 이미 끝난 작업에는 608을 돌려준다. 중단 신호를 받은 작업 실행기는 현재 스텝을 마친 뒤 GPU를 해제하고 상태를 CANCELLED로 바꾼다. 중단한 작업의 체크포인트는 등록 대상이 아니며, 남은 변환 · 평가 · 등록도 실행하지 않는다.

### 6.4.7 학습 파라미터 조회 · 수정 (T-08)

4.3에서 확정한 파라미터를 기본 설정으로 두고 재학습에도 같은 값을 쓴다.

[그림: 학습 파라미터 조회 · 수정 sequence diagram — 다시 그림]

AI 담당자가 값을 바꾸면 학습서버가 허용 범위(학습률 1e-6~1e-4, 에폭 1~10, 어려운 오답 수 1~3, 배치 8 · 16. 실효 배치는 그래디언트 누적으로 조절)를 검사하고, 벗어나면 603을 돌려준다. 저장할 때 이전 값을 이력으로 남겨 각 모델 버전이 어떤 설정으로 학습됐는지 추적한다.

### 6.4.8 모델 평가 · 임계값 결정 (T-09)

학습된 모델의 성능을 재고 서비스에서 쓸 τ를 정한다.

[그림: 모델 평가 · 임계값 결정 sequence diagram — 다시 그림]

작업 실행기는 서비스와 같은 fp16 모델로 평가한다.

1. 검증셋에서 fp32 체크포인트 대비 질문 단위 ROC-AUC 하락이 0.01 이하인지 확인한다.
2. 질문마다 후보 20개 점수의 최고값으로 τ를 정한다. τ는 실제로 나온 점수값 중 FPR이 4% 이하인 가장 낮은 값이며, 점수가 τ와 같으면 답변으로 본다.
3. 시험셋에서 τ를 고정한 채 질문 단위 ROC-AUC · 오답 즉답률 · TPR을 95% 오차 범위와 함께 재고, 라벨별 이관율(의견 질문 이관율 포함) · 질문 출처별 결과 · 쌍 단위 ROC-AUC(보조)를 남긴다. 시험셋 결과를 보고 τ를 고치지 않는다.
4. 판정 모델 평가에는 정답 근거가 후보에 든 답변 가능 질문과 이관 대상 질문만 쓴다. 시험셋 전체로는 검색 성공률 · 검색 실패 시 즉답률 · 근거 적중률(top-1)을 따로 계산해 9.1에 넘긴다.
5. 같은 시험셋으로 베이스라인 3종(SIMILARITY / PRETRAINED / SONNET_ONLY)을 잰다. SONNET_ONLY는 서비스 LLM_ONLY와 같은 프롬프트로 질문과 후보 20개를 한 번에 주고 0~100 점수와 근거 최대 5개를 받으며, 검증셋에서 τ와 같은 규칙으로 τ_LLM을 정한다. 검증 · 시험셋 버전, Sonnet 모델 ID, 프롬프트 버전, τ 선정 규칙이 모두 같으면 베이스라인 결과를 재사용한다. 베이스라인 1 · 2는 데이터셋 버전만 같으면 재사용한다.
6. 판정 모델 버전 하나의 시험셋 평가가 처음 등록 판단에 쓰이면 그 시험셋 버전의 사용 횟수(test_use_count)를 1 올리고 그 값을 평가 결과에 남긴다. 같은 모델을 다시 평가하거나 베이스라인만 잰 경우는 올리지 않는다.

자동 연결 학습(6.4.5)에서는 이 평가가 학습 작업의 한 단계로 실행되고, 평가 API는 AI 담당자가 변환본이나 등록 버전을 따로 평가할 때 쓴다.

### 6.4.9 버전 비교 (T-10)

재학습한 모델을 배포해도 되는지 판단한다.

[그림: 버전 비교 sequence diagram — 다시 그림]

두 버전의 평가 결과를 같은 시험셋 버전 기준으로 비교하고, 그 시험셋 버전의 평가가 없는 쪽은 6.4.8의 평가를 먼저 실행한다. 새 버전이 등록 조건을 만족하고 질문 단위 ROC-AUC가 기준 버전과 같거나 높을 때만 deployable = true다. 이 비교는 버전 등록 직후 자동으로 실행되어 모델의 deployable로 저장되고(서빙 중인 모델이 없으면 등록 조건만 본다), 관리자 웹은 이 값으로 전환 버튼을 켜거나 끈다(F12-4). 실제 전환(6.4.11) 때는 그 시점의 서빙 버전과 다시 비교한다.

### 6.4.10 fp16 변환 · 모델 버전 등록 (T-11, T-12)

학습된 모델을 서빙 형태로 바꾸고 버전으로 등록한다.

[그림: fp16 변환 · 모델 버전 등록 sequence diagram — 다시 그림]

변환 작업은 fp32 체크포인트를 fp16으로 바꿔 model.safetensors로 저장하고, 학과 서버 GPU에서 질문 1개의 후보 20쌍 추론 시간(p95)을 잰다. 변환 중 오류가 나면 604를 기록한다. 변환본은 평가(6.4.8)를 거쳐 fp16 하락과 등록 조건을 확인받는다. 등록 API는 등록 조건(추론 시간 p95 ≤ 500 ms 포함)을 넘은 평가만 받고(못 넘으면 615), 패키지를 /data/easyq/models/judge-vN/에 저장해 지표 · τ와 함께 REGISTERED로 등록한 뒤 서빙 버전과 비교해 deployable을 저장한다. 자동 연결 학습에서는 변환 · 평가 · 등록이 학습 작업의 한 단계로 실행되며, 이 API들은 AI 담당자가 수동으로 변환 · 등록할 때 쓴다.

### 6.4.11 서빙 버전 전환 (T-13)

등록된 버전을 강연 중 실제 판정에 쓰도록 바꾼다.

[그림: 서빙 버전 전환 sequence diagram — 다시 그림]

학습서버는 요청한 버전을 현재 서빙 버전과 비교해(6.4.9와 같은 기준, 서빙 중인 모델이 없으면 등록 조건만) 미달이면 614로 거부한다. 통과하면 패키지를 추론 프로세스의 GPU 메모리에 기존 모델과 나란히 올리고, 시험 질문 5건으로 점검한 뒤에만 교체한다. 그래서 강연 중에 배포해도 판정이 끊기지 않는다. 적재나 점검에 실패하면 기존 버전을 유지하고 605를 기록한다. 성공하면 서빙 설정에 새 버전의 τ와 그 버전 평가의 베이스라인 3 결과(τ_LLM · Sonnet 모델 ID · 프롬프트 버전)를 기록하고, 서빙 이력(served_before)을 남긴다. 서빙한 적 있는 버전으로 돌아갈 때는 롤백(6.4.12)을 쓴다.

### 6.4.12 롤백 (T-14)

새 버전에서 운영 지표(철회 · 대체 판정 증가 등)가 나빠졌을 때 되돌린다.

[그림: 롤백 sequence diagram — 다시 그림]

롤백 대상은 서빙한 적 있는 버전과 LLM_ONLY다. 버전은 직전 서빙 버전(previous)이나 서빙 이력이 있는 버전 이름으로 지정하며, 이미 서빙해 검증된 버전이므로 배포 비교 없이 다시 적재한다. 서빙 이력이 없거나 삭제된 버전이면 610을 돌려준다. LLM_ONLY로 롤백하면 판정 모델을 쓰지 않도록 서빙 모드를 바꾸고, 서빙 설정의 τ_LLM · Sonnet 모델 ID · 프롬프트 버전은 그대로 두어 서비스가 모든 질문을 LLM_ONLY로 판정하게 한다(F9-6). LLM_ONLY에서 판정 모델로 돌아갈 때도 서빙했던 버전을 지정한다.

### 6.4.13 모델 버전 메모 수정 · 삭제 (T-16)

버전마다 실험 내용을 메모하고 쓸모없는 버전을 정리한다.

[그림: 모델 버전 메모 수정 · 삭제 sequence diagram — 새로 그림]

서빙 중인 버전과 직전 서빙 버전은 삭제할 수 없다. 삭제하면 모델 저장소의 패키지는 지우고, 레지스트리의 지표 기록은 DELETED 상태로 남겨 버전 비교 이력을 유지한다.

### 6.4.14 판정 추론 · 서버 상태 확인 (T-18, T-19)

강연 중 질문마다 판정 모델을 호출하고, 학과 서버에 문제가 있어도 서비스가 멈추지 않게 한다.

[그림: 판정 추론 · 상태 확인 sequence diagram — 새로 그림]

서빙 어댑터는 10초마다 상태 확인 API로 현재 서빙 모드 · 버전 · τ를 확인한다. 질문이 오면 RRF로 합친 후보 20개를 한 번에 보내고, 추론 프로세스는 GPU에 상주한 fp16 모델로 한 배치에 점수를 매겨 재정렬한 결과와 판정을 돌려준다. 터널이 끊기거나 응답이 800 ms를 넘기거나 611을 받으면 그 질문만 LLM_ONLY로 넘어간다. 어느 경로를 썼는지와 실제 적용된 모델 버전 · τ는 처리 로그(F4-7)에 남긴다.

### 6.4.15 장애 기록 · 조회 (T-20, T-21)

학습서버에서 나는 오류를 남기고 원인을 찾는다.

[그림: 장애 기록 · 조회 sequence diagram — 새로 그림]

작업 중 예외가 나면 작업 실행기가 오류 코드 · 작업 번호 · 모듈 · 메시지를 레지스트리와 장애 로그 파일(8.3)에 함께 남기고 작업을 FAILED로 바꾼다. AI 담당자는 학과 서버에서 기간 · 코드 · 작업으로 걸러 조회하고, 관리자 웹은 학습 작업 상태의 오류 코드로 실패를 확인한다.

### 6.4.16 평가용 교안 조각 제공 (T-22)

서비스가 강연을 평가용 강의로 자동 표시하는 데 쓸 교안 조각을 제공한다(6.1.6).

[그림: 평가용 교안 조각 제공 sequence diagram — 새로 그림]

데이터셋을 등록할 때(6.4.1) 학습서버는 평가용 강의(6.0001 · 6.172 · 자체 녹음 강의)의 교안을 서비스와 같은 방식으로 나눈 조각을 평가용 교안 조각 목록(es-vN)으로 만든다. worker가 가진 목록 버전을 보내면, 최신과 같을 때는 빈 목록을, 다를 때는 새 목록과 일치 기준(5단어 묶음, 조각 일치 80%, 강연 판정 30%)을 돌려준다. 목록에는 평가용 강의의 교안 텍스트만 들어가고 AI Hub 데이터와 평가 질문은 없다. 평가용 강의를 통째로 다시 하면 조각이 거의 모두 일치해 걸러지고, 일부 페이지만 참고로 쓴 강연은 통과시키되 그 페이지에 달린 쌍은 병합 전 겹침 검사(6.4.3)로 뺀다.
