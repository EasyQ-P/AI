# 4장 AI학습모델의 설계 — 수정본

> 표 · 그림 번호는 통합 때 매긴다. 그림 4장(파이프라인 · 판정 방식 비교 · 패키지 생성 · 서비스 이용)은 이 본문에 맞춰 다시 그린다.

## 4.1 모델 파이프라인의 구성

판정 모델은 ① 데이터셋 버전 → ② 학습 입력 구성 → ③ 파인튜닝 → ④ fp16 변환 → ⑤ 평가 · 임계값 → ⑥ 등록 · 배포의 6단계로 만들어지고, ⑦ 피드백 재학습으로 다시 ①로 돌아온다. ②~⑥은 AI학습서버(학과 서버 GPU)에서 실행되며, 학습서버 API(7.4)로 제어한다.

fp16 변환을 평가보다 먼저 하는 이유는 서비스가 fp16 모델로 판정하기 때문이다. τ와 9.2의 기준을 서비스와 같은 모델로 재야 서비스에서도 같은 오답 즉답률이 나온다. 판정 모델은 강연 중 질문마다 근거 후보 20개를 800 ms 안에 채점해야 하므로, 학과 서버 GPU에 fp16으로 상주시켜 추론한다. fp16은 fp32의 절반 메모리로 GPU에서 빠르게 계산되며, 정확도 손실은 검증셋에서 확인해 0.01 이하일 때만 등록한다.

**라벨 변환 규칙.** 3.3의 라벨은 세 가지(ANSWERABLE 답변 가능 / INSUFFICIENT_EVIDENCE 근거 부족 / OPINION 의견 질문)이지만, 서비스의 결정은 "AI가 답한다 / 강연자에게 넘긴다" 두 가지다. 그래서 답변 가능을 1, 나머지를 0으로 만든다(target). 의견 질문("교수님은 어느 쪽을 추천하세요?")은 관련 근거가 있어도 0이다.

**학습셋 구성.** 질문 약 3,000개로 만든다. MIT OCW 학습 강좌 3개(6.006 · 6.046J · 6.034)의 합성 질문 2,000개(답변 가능 700 / 근거 부족 700 / 의견 600), SQuAD 2.0 train 500개(답 있음 250 · 없음 250), AI Hub 기계독해 500개(정답 있음 250 · 없음 250)다. 질문 기준 라벨 비율은 40 / 40 / 20이다. SQuAD · AI Hub 지문은 서비스 근거 길이(발화 청크 약 60단어, 교안 조각)로 자른다. 답이 있는 질문은 정답 문장 주변, SQuAD의 답 없는 질문은 plausible_answers가 가리키는 문장 주변, AI Hub의 정답 없는 질문은 질문과 겹치는 단어가 가장 많은 조각(BM25)을 쓴다. 검수를 마친 서비스 피드백 라벨은 학습셋에만 더한다.

**어려운 오답.** MIT OCW 답변 가능 질문마다, 같은 강의에서 서비스와 같은 검색(벡터 검색과 형태소 분석 키워드 검색을 RRF로 합친 상위 20개)으로 나온 후보 가운데 정답 근거가 아닌 조각을 1~3개 붙인다. 붙인 조각은 Sonnet으로 "이 근거로 답할 수 있는가"를 다시 확인해 답이 있으면 뺀다. 주제는 비슷하지만 답이 없는 근거를 0으로 배워야, 강연 중에 "비슷한 내용이 있으니 답한다"는 오답을 줄일 수 있다. SQuAD · AI Hub는 정답 없는 질문이 그 자체로 어려운 오답이라 따로 뽑지 않고, AI Hub에는 임베딩을 쓰지 않는다. 오답 쌍이 붙어 쌍 기준 라벨 비율은 약 27 / 59 / 14가 되고, 이 불균형은 BCE의 양성 가중치로 보정한다(4.3).

**검증 · 시험셋 구성.** 검증 · 시험셋은 서비스와 같은 질문 단위 형식이다. 한 행에 질문 1개, 서비스 검색으로 뽑아 고정한 후보 20개, 질문 단위 라벨, 후보 중 답이 든 조각 전부(gold_evidence_ids), 그 조각이 후보에 있는지(gold_in_candidates)를 둔다. 검증셋은 6.0001 질문 약 450~500개(이관 대상 300 이상)다. 시험셋은 6.172(영어 교안 · 전사본)와 동의받은 자체 녹음 1강(실제 STT)의 질문 600개 이상(이관 대상 400 이상, 그중 의견 100 이상)이며, 2인이 먼저 붙인 사람 라벨만 쓴다. 검증 · 시험셋에는 SQuAD · AI Hub를 넣지 않는다. 필드 이름은 3.3.3을 따른다.

**질문 단위 판정.** 모델은 (질문, 근거) 쌍마다 점수를 내고, 질문의 최종 판정은 후보 20개 점수 중 최고값이 τ 이상인지로 정한다(F4-2). 평가(⑤)도 이 질문 단위 규칙으로 해야 서비스 성능과 숫자가 같아진다. 판정 모델 평가에는 정답 근거가 후보에 든 답변 가능 질문과 이관 대상 질문만 쓴다. 검색이 정답 근거를 놓친 질문은 판정 모델의 실수가 아니기 때문이다.

## 4.2 AI학습 알고리즘의 선정

판정 모델은 딥러닝 기반 **이진 분류**로 하며, 알고리즘은 질문과 근거를 한 입력으로 읽는 **크로스인코더(bge-reranker-v2-m3) 파인튜닝**을 선정한다. 서비스가 내려야 하는 결정이 "답한다 / 넘긴다" 두 가지이고, 오답 즉답률 ≤ 5%를 맞추려면 점수의 기준선(τ)을 움직여 조절할 수 있는 확률 출력이 필요하기 때문이다.

[그림: 판정 방식 비교 — (b)를 채택하고 (a) · (c)는 베이스라인으로 쓴다 — 다시 그림]

**분류와 회귀.** 라벨이 "답변 가능 여부"라는 범주이므로 회귀가 아닌 분류다. 세 라벨을 그대로 쓰는 3중 분류도 검토했지만, 근거 부족과 의견 질문은 서비스에서 같은 처리(이관)를 받고, ROC-AUC와 임계값은 이진 점수에서 바로 계산된다. 그래서 이진 분류로 한다. 다만 이진 점수의 ROC-AUC만 보면 의견 질문을 제대로 넘겼는지 드러나지 않는다. 그래서 평가(T-09)에서 라벨별 이관율을 따로 계산하고, 의견 질문 이관율(의견 질문 중 ESCALATE로 판정된 비율)로 "근거가 있어도 넘겨야 하는 질문"을 실제로 걸러내는지 확인한다. 목표는 95% 이상이다(9.1).

**크로스인코더를 쓰는 이유.** 임베딩 유사도(a)는 질문과 근거를 따로 벡터로 바꿔 비교하므로 "주제가 비슷하다"까지만 알 수 있다. 크로스인코더(b)는 두 문장의 토큰이 24개 층에서 서로 어텐션하므로 "이 근거에 질문의 답이 들어 있는가"를 판단할 수 있다. 또 점수 하나로 근거 재정렬(답변에 쓸 상위 5개 선택)과 게이트(답 / 이관)를 함께 처리해 모델 하나만 서빙하면 된다.

**bge-reranker-v2-m3를 쓰는 이유.**

- 다국어 사전학습 모델(XLM-RoBERTa 계열)이라 한영 혼용 강의의 질문 · 교안 · 발화를 한 모델로 처리한다.
- 이미 검색 재정렬용으로 학습된 모델이라, 처음부터 학습하는 것보다 적은 라벨 데이터로 "답변 가능" 기준을 익힐 수 있다.
- 공개 가중치라 학과 서버에서 직접 파인튜닝하고 fp16으로 서빙할 수 있다. 파라미터 약 5.7억 개로, fp16 가중치는 GPU 메모리 약 1.1 GB를 차지한다.

**LLM 단독 판정을 쓰지 않는 이유.** Sonnet 단독 판정(c)은 질문과 후보 20개를 한 번에 읽고 0~100 점수를 내므로, 같은 규칙으로 임계값(τ_LLM)을 정해 비교할 수 있다. 하지만 질문마다 호출 비용과 지연이 들고, 팀이 직접 학습 · 재학습할 수 없다. 또 점수가 정수 단위라 같은 점수가 많아 임계값을 세밀하게 조절하기 어렵다. 따라서 판정 모델 장애 시의 대체 경로(LLM_ONLY, F4-3)와 베이스라인 ③으로만 쓴다. 베이스라인 ③과 서비스의 LLM_ONLY는 같은 프롬프트 · 같은 방식이라, 9.2의 베이스라인 ③ 결과가 곧 장애 때 서비스의 판정 성능이다.

## 4.3 AI학습 파라미터 설정

학습 파라미터는 아래 초기값으로 시작하고, 예비 학습에서 학습률과 어려운 오답 수만 작은 격자 탐색(3 × 3 = 9회)으로 확정한다. 선택 기준은 시험셋이 아닌 **검증셋 질문 단위 ROC-AUC**이며, 확정한 값은 T-08(학습 파라미터 수정)로 학습서버의 기본 설정에 저장해 재학습에도 같은 값을 쓴다.

| 난수 시드 | 42, 43, 44 | — | 확정한 설정으로 시드 3개를 학습해 검증셋 AUC가 가장 높은 체크포인트를 쓰고, 세 시드의 평균과 표준편차를 함께 기록해 우연한 결과를 가려낸다 |

학습이 아닌 **서비스 판정 파라미터**는 학습이 끝난 뒤 따로 정한다.

표: 서비스 판정 파라미터

| 파라미터 | 값 | 정하는 방법 |
|---|---|---|
| 판정 임계값 τ | 모델 버전마다 다름 | 서비스가 쓰는 fp16 모델의 검증셋 질문 단위 최고 점수에서, FPR(오답 즉답률) 4% 이하를 만족하는 점수값 중 가장 낮은 값으로 정해 manifest에 기록한다. 점수가 τ와 같으면 답변으로 본다. 만족하는 값이 없으면 τ를 최고 점수보다 높게 두어 모든 질문을 이관한다. 목표(5%)보다 1%p 낮게 잡는 것은 검증셋(합성 발화)과 시험셋(실제 STT) 차이로 시험셋 FPR이 높게 나오기 쉽기 때문이다. 시험셋은 이 τ에서 성능만 잰다 |
| LLM_ONLY 임계값 τ_LLM | Sonnet 모델 · 프롬프트마다 다름 | 베이스라인 ③의 검증셋 0~100 점수에 τ와 같은 규칙을 적용한다. 만족하는 점수가 없으면 101로 둔다. 서빙 설정에 Sonnet 모델 ID(날짜가 붙은 고정 ID) · 프롬프트 버전과 함께 기록한다 |
| 근거 후보 수 | 20 | 같은 강연에서 벡터 검색 20개와 형태소 분석 키워드 검색 20개를 RRF로 합친 상위 20개 (F4-1) |
| 답변에 쓰는 근거 수 | 최대 5 | 점수 ≥ τ인 근거 중 상위 5개에 앞뒤 문맥을 붙인다 (F4-4). LLM_ONLY는 Sonnet이 고른 근거 최대 5개 |
| fp16 허용 하락폭 | 0.01 이하 | fp32 대비 fp16의 검증셋 질문 단위 ROC-AUC 하락. 넘으면 등록하지 않고 HELD(precision_drop)로 멈춘다 |
| 추론 시간 기준 | p95 ≤ 500 ms | 질문 1개(후보 20쌍)를 학과 서버 GPU에서 fp16으로 채점하는 시간. 판정 타임아웃 800 ms 안에 SSH 터널 왕복 시간을 남기기 위한 값이며, 넘으면 등록하지 않는다 |
| 판정 타임아웃 | 800 ms | 서비스가 판정 응답을 기다리는 최대 시간. 넘으면 그 질문만 LLM_ONLY로 판정한다 |

## 4.4 AI학습 모델의 생성

학습의 최종 결과물은 **모델 패키지 judge-vN**(fp16 가중치 + 토크나이저 + manifest)이며, 학과 서버 모델 저장소에 두고 버전 레지스트리에 등록한다. 서비스는 이 패키지를 적재한 판정 추론 API를 불러 질문마다 "AI 답변 / 강연자 이관"을 정한다.

### 4.4.1 생성 과정

[그림: 판정 모델 패키지 생성 과정 — 다시 그림]

1. **최적 체크포인트 선택**: 학습 중 검증셋 질문 단위 ROC-AUC가 가장 높았던 에폭의 가중치를 fp32로 남긴다(T-05).
2. **fp16 변환**: fp32 가중치를 fp16으로 변환해 model.safetensors로 저장하고, 학과 서버 GPU에서 질문 1개의 후보 20쌍 추론 시간을 잰다(T-11).
3. **평가 · 임계값**: fp16 모델로 검증셋에서 fp32 대비 질문 단위 ROC-AUC 하락(≤ 0.01)을 확인하고 τ를 정한 뒤, 시험셋으로 질문 단위 ROC-AUC · 오답 즉답률 · TPR · 라벨별 이관율과 베이스라인 3종을 잰다(T-09).
4. **등록**: 등록 조건(fp16으로 잰 질문 단위 ROC-AUC ≥ 0.85, 시험셋 오답 즉답률 ≤ 5%, 그 지점 TPR ≥ 0.5, 베이스라인 3종보다 ROC-AUC 높음, 검증셋 AUC 하락 ≤ 0.01, 추론 시간 p95 ≤ 500 ms)을 모두 만족하면 model.safetensors, tokenizer/, manifest.json을 학과 서버 /data/easyq/models/judge-vN/에 두고 버전 레지스트리에 REGISTERED로 넣는다. 하나라도 못 넘으면 등록하지 않는다(T-12).
5. **배포**: 같은 시험셋 버전에서 서빙 중인 버전보다 질문 단위 ROC-AUC가 같거나 높을 때만 관리자가 서빙 버전을 바꾼다. 서빙 중인 모델이 없으면 등록 조건만 본다(T-10, T-13).

manifest.json에는 서비스가 그대로 쓰는 값이 들어간다(수치는 형식을 보여주기 위한 예시다).

### 4.4.2 출력 결과

모델은 (질문, 근거) 쌍마다 **답변 가능 확률(0~1)**을 낸다. 추론 API는 후보 20개의 점수를 높은 순으로 재정렬하고, 최고 점수를 τ와 비교해 질문 단위 판정(ANSWER / ESCALATE)과 답변에 쓸 근거(최대 5개)를 돌려준다. 입출력 형식은 7.4의 판정 추론 API(T-18)를 따른다.

### 4.4.3 서비스에서의 이용

[그림: 서비스에서 판정 모델을 이용하는 방식 — 다시 그림]

- 청중 질문이 들어오면 worker가 같은 강연의 교안 · 발화에서 벡터 검색 20개와 형태소 분석 키워드 검색 20개를 RRF로 합쳐 근거 후보 20개를 만들고, 서빙 어댑터가 SSH 터널을 통해 학과 서버의 판정 추론 API를 호출한다. 이때 질문자 화면에는 "근거를 찾는 중" 상태가 표시된다.
- 최고 점수 ≥ τ이면 상위 근거(최대 5개)에 앞뒤 문맥을 붙여 Sonnet이 4문장 이내로 답변하고, 질문자 화면에는 "답변을 작성하는 중" 상태와 함께 답변이 나타난다. Sonnet이 근거가 부족하다고 판단하거나 인용 검증을 통과하지 못하면 답변을 내보내지 않고 이관한다. 최고 점수가 τ 미만이면 Sonnet을 부르지 않고 공개 목록으로 이관한다.
- 판정 추론 프로세스는 서빙 버전의 fp16 모델을 학과 서버 GPU 메모리에 상주시키고, 학습 · 평가 · 변환 작업이 GPU를 쓰는 중에도 판정에 응답한다.
- 터널이 끊기거나 응답이 800 ms를 넘기면 그 질문만 LLM_ONLY로 판정한다. 질문과 후보 20개를 Sonnet에 주고 0~100 점수와 근거 최대 5개를 받아, 점수가 τ_LLM 이상이면 고른 근거로 답변하고 미만이면 이관한다. 어느 경로로 판정했는지 처리 로그(F4-7)에 남긴다.
- 새 버전을 배포하면 추론 프로세스가 학과 서버 모델 저장소의 패키지를 기존 모델과 나란히 적재하고 점검한 뒤 교체한다. 서비스 서버는 코드 변경 없이 서빙 설정 조회(7.4)로 받은 새 τ · τ_LLM을 쓴다.
